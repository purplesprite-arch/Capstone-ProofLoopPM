Full design + next-steps detail for every roadmap card, one section per epic. This is the source of truth the roadmap grid summarizes — nothing here is built yet except this document itself.

EFoundation

Features data model M · in design

There is currently no features/epics entity in prototype-2/data.js — the Build View and the decision↔feature map both need one. Proposed shape:

  • id, name, agentId, status, summary, progress, decisionIds[], jiraKey?, blockers[]
  • status ∈ backlog | in-progress | build-complete | piloting | live
  • Join key today: agentId and/or a decision id — no new keying scheme required.

Worker /api groundwork rolled into Foundation

The Cloudflare Worker's /api/* route currently returns a 501 stub. /api/jira becomes the landing spot for the read-only Jira sync (Appendix D) once Foundation lands.

FPresenter Mode — live stakeholder-review cockpit

A desktop / projector-focused decision cockpit the decider runs in front of stakeholders — walk each decision, discuss, and approve live in the room. Distinct from the mobile morning ritual; this is its "big screen" counterpart.

Entry point S · in design

On the open-the-app time picker (zero / some / lots of time), add a fourth, grey secondary affordance labelled "Presenter Mode" — grey signals it's a different mode, not a fourth time choice. Selecting it routes to the cockpit instead of the mobile ritual. Implementation hook: add a presenter route to the valid whitelist (app.js) and a presenter(state) render function.

The cockpit L · in design

  • Layout tuned for live review: big type legible at distance, calm spacing, one decision in focus at a time with the rest listed compactly so the room can follow.
  • Shows decisions and build items on one screen. Each decision shows its impact, recommendation + rationale, key evidence, and any attached conditions or guardrails. Each build item shows status and which decisions block or inform it.
  • Inline actions: small Approve / Revise / Reject buttons per decision, reusing the existing data-decide + confirm flow in app.js — no new decision engine. Actioning a blocking decision updates its build item live.
  • Reuses existing renderers (brief, compactCard, scoreBadge) rather than inventing new ones.

Present-mode polish M · planned

Legibility at distance, focus-one-at-a-time transitions, keyboard navigation (next / prev / approve), and a clean full-screen takeover that hides mobile chrome.

Sizing note: the cockpit reuses the decide/confirm pipeline, so it does not depend on Foundation for decisions — but its build-item rows do, so the richest version follows the Foundation lane.

A2 · Value Focus M · in design

Role-play framing: a KPI/value SME's job is to make this section land instantly with an executive, in their own language, without turning into a dashboard. The stakeholder picks 2–3 focus areas; each shows a primary metric plus supporting KPIs. Selected focuses later re-rank the decision queue by impact (ties to the existing impact sub-scores). A4 · Preference refinements & brainstormed ideas M · planned

v1 ships A1–A3 + Value Focus only, to avoid bloat. The rest is sequenced here as "Later":

  • Risk tolerance slider (conservative ↔ aggressive) + an auto-advance confidence threshold — what % lets informational items advance without me (ties to the existing autoIn field).
  • Delegation defaults by domain (ties to the existing delegateTo field).
  • Locked commitments I personally own (e.g. the 30-second handoff promise) — a short pinned list.
  • Auto-generated "decision style" from Memory (approve/revise/reject ratio) — a self-aware mirror, no manual input required.
  • Trust threshold — minimum evidence-coverage % before I'll approve.
  • Impact-to-date scorecard ($ saved, decisions made, avg time-to-decide) — reinforces exec value every time the profile is opened.

DJira & agile-board integration

Hard constraint from the brief: no extensive configuration in either tool, no ongoing maintenance burden. If keeping ProofLoop updated means heavily instrumenting Jira, the point of the tool has been missed. Staged path, fitting the Worker's already-stubbed /api/*:

1
Spike S · in design

Confirm the auth model (API token vs. OAuth), whether JQL-by-label is sufficient to find relevant issues, and the shape of a status-map config — before committing to any sync build.

2
Read-only, label-driven, status-mapped sync L · planned — recommended

In Jira: add one label (e.g. proofloop) to relevant issues — no custom fields. In ProofLoop: store a jiraKey (or a saved JQL) per feature. The Worker calls the Jira REST search with a single API token, reads status + summary, and maps Jira status → ProofLoop feature status via a tiny status-map (Done→build-complete, In Progress→in-progress, …). This is the whole integration — cheap to set up, near-zero upkeep.

no custom fields one label one API token

·
Optional: near-real-time push

A single Jira Automation rule POSTs issue transitions to /api/jira — no polling, and no ProofLoop-side Jira credentials needed for the push.

3
Two-way sync XL · planned — parked

ProofLoop creating or transitioning Jira issues. This is exactly the high-maintenance, "we're now managing two tools instead of one" scenario the brief warned against — parked at maybe-never unless a concrete need emerges.
